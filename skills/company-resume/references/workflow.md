# 파일과 작업 절차

## 비공개 작업 디렉터리

저장소 외부(예: `~/Documents/ResumeWorkspace/`)에 아래 자료를 둔다. 아래는 파일의 역할이며 빈 파일을 모두 생성할 필요는 없다. 공개 repo에 이 디렉터리를 연결하거나 복사하지 않는다.

- `facts/evidence.json`: 주장 ID, 원문, 출처 파일/라인과 SHA-256, 검토 상태(`source-only`, `user-confirmed`, `artifact-verified`), 기여 범위, 기간, 수치 측정 조건, 공개 가능 범위. 역할과 수치는 개별적으로 검증한다.
- `facts/questions.md`: 주장의 정확성/기여 범위/측정 조건/사용 허가에 관한 정확한 누락.
- `applications/<company-role>/job.md`: 공고 URL, 조회일, 요구사항 요약. Platform/Product는 서로 다른 요구사항이다.
- `applications/<company-role>/mapping.md`: 요구사항 → 증거 ID → 강조/보류 경험 → 선정 이유 → 근거 부족. 문장보다 먼저 만든다.
- 최초 작성은 회사별 폴더에 새 `resume-v1.json`, `resume-v1.md`, `resume-v1.pdf`를 AI가 생성한다. 사용자 export는 필요 없다. 이후 사용자가 편집한 문서를 다시 수정할 때만 `latest.json`, `scope.json`, `plan.json`, 새 후보 폴더를 사용한다. 최신 export는 수동 편집 후마다 새 파일로 저장한다.

자료 정리는 특정 자료만 확인한다. 비밀값/계좌 파일과 관계없는 개인 폴더를 조사하지 않는다. 소스에 적힌 수치만으로 측정 조건까지 추론하지 않는다.

## 초안

AI가 기존 경력 자료로 첫 원고를 먼저 완성하고, 사용자가 그 결과를 확인·수정한다. 최초 작성에는 최신 JSON export, scope, plan, 원본 hash가 필요 없다. 이름과 회사·경력·기술 등 자료에서 확인한 내용을 사용해 새 문서와 고유한 초기 페이지/블록 ID를 생성한다. `validate`로 검사한 JSON을 기존 앱에 새 이력서로 가져온다.

현재 공고를 직접 읽고 요구사항과 근거를 연결한다. 직접 경험과 인접 경험을 구분하며 출처가 있는 정성적 기여를 완결된 소개·경력·프로젝트 문장으로 쓴다. 검증되지 않은 성과 숫자나 없는 경험을 보충하지 않는다. 근거가 부족한 주장은 제외하고, 나머지 원고는 끝까지 작성한다. 기능 테스트용 빈칸이나 질문 목록을 첫 원고의 대용으로 전달하지 않는다. 기존 빈 PAR의 허구 보충을 피하려고 작업을 멈추지 말고, 첫 작성에서는 근거가 있는 내용에 맞는 단락/불릿 블록을 선택한다.

검토용 JSON·Markdown·PDF를 공개 저장소 밖 새 경로로 저장하고 실제 앱 가져오기와 PDF 렌더링을 확인한다. 질문은 별도 파일에 꼭 필요한 것만 최대 3개로 두고, 본문을 확인 경고로 채우지 않는다. 직무가 미확정이면 회사/직무별 첫 버전임을 파일 메타데이터와 전달 설명에 명시한다. 사용자가 편집하기 전 첫 원고 완성 자체를 위해 export를 요청하지 않는다.

ClickUp/GitLab 조사를 요청받으면 실제 담당자, MR 작성자·병합 상태, 변경 파일과 검증 기록을 확인해 비공개 근거에 남긴다. 초기 태스크 계획과 최종 구현이 다르면 병합된 구현을 기준으로 쓴다. `resolved`만으로 모든 제안의 실제 반영을 단정하지 않는다. MR의 성능 비교 조건·표본·제약을 확인하기 전 숫자를 옮기지 않는다. 내부 URL·고객명·민감한 원문은 공유 원고에 넣지 않는다.

문장은 **한 문장에 한 핵심 기여 또는 임팩트**를 기준으로 쓴다. 같은 설계의 선택과 직접 결과는 함께 설명할 수 있지만 CI·테이블·리사이즈처럼 서로 다른 성과는 별도 불릿으로 나눈다. 소개는 2~3문장 이내로 쓰고 프로젝트의 짧은 불릿을 반복하는 핵심 기여 목록은 줄인다. 학력은 기술과 분리한다. 실제 작업 기간을 모르면 MR 생성일부터 병합일까지를 프로젝트 전체 기간으로 만들지 않는다. 필요한 경우 검증된 시점을 “2026.08 병합”처럼 사건으로 명시한다. MR 작성자·태스크 담당자 기록은 해당 변경의 기여 근거이며 프로젝트 전체 단독 수행이나 팀 규모의 증거가 아니다.

각 경험은 처음 읽는 사람이 **무엇의 문제였는지, 어떤 제약 때문에 그 방식을 골랐는지, 이전과 무엇이 달라졌는지**를 설명할 수 있어야 한다. 한 문장 한 핵심은 서로 무관한 기여를 묶지 말라는 기준이며, 문장 사이의 문제·선택·결과 연결을 삭제하라는 뜻이 아니다. 짧은 기능 목록만 남으면 원고를 다시 쓴다. 특정한 PAR 라벨이나 고정 불릿 수를 강제할 필요는 없다.

선택 이유는 MR·태스크의 배경, 측정, 명시된 설계 경계와 대조한다. 기록이 방식만 설명하면 더 그럴듯한 동기나 검토하지 않은 대안을 보충하지 않는다. 당시 제약에 대응하는 선택이라는 점까지만 쓴다. 결과는 수치 외에도 새로 가능해진 작업, 없어진 중복 구현, 유지되는 사용자 조작, 검증된 상태 변화로 쓸 수 있다. 검증 방법과 통과 범위를 원문보다 넓히지 않으며, 남은 비용·제약도 완료된 성과와 구분한다.

문체를 다듬을 때 “실행 대상과 구성 정의를 분리”를 “어디에 띄울지와 어떻게 구성할지를 나눔”으로 바꾸지 않는다. API·엔진·어댑터·Node/jsdom·requestAnimationFrame 등 독자의 이해에 필요한 용어는 유지한다. 숫자는 비교 대상·표본·제외 조건·원자료의 한계를 함께 확인하며, 당시 기록을 재측정 결과로 제시하지 않는다.

완성 원고에 설치된 `humanizer`를 적용해 명사 나열·모호한 표현·반복 구조를 다듬는다. 기술 용어는 보존하고 이력서의 격식체를 유지한다. 이후 문제 → 본인의 선택 → 구현/검증 결과가 읽히는지, 협업을 단독 성과로 넓히지 않았는지, 교정으로 새 사실이나 수치가 생기지 않았는지 검토한다. 교정 전후에 문제의 대상·제약, 선택 이유, 결과의 연결이 남아 있는지도 확인한다. 접속사를 줄이거나 문장을 짧게 만들기 위해 이 맥락을 없애지 않는다. 수정 전후와 근거 대조 결과는 비공개로 기록한다. 공개 배포는 사용자 지시가 있을 때만 하며 승인된 저장소·기존 배포 경로·필요 파일에 한정한다.

실제 앱 registry 16개 타입은 `header`, `positioning`, `sectionHeader`, `coreImpact`, `careerHeader`, `careerProject`, `par`, `caseStudyHeader`, `caseStudyOutcome`, `skills`, `learningNote`, `education`, `freeText`, `blogPosts`, `divider`, `spacer`다. 타입별 필드는 `scripts/resume-schema.ts`와 대상 앱 `types.ts`를 확인한다. `theme`은 현재 `default`/`mono`다. 초안에서도 기본 예시 문구나 placeholder를 경력으로 채택하지 않는다. 필수 문자열은 빈 문자열로 둘 수 있지만 제출 준비 완료를 의미하지 않는다.

## 부분 수정 형식

사용자 요청 예: “소개 두 번째 문장의 표현만 바꿔줘.” 필드 내 일부 문장만 요청했다면 target에 `range: [start, end]`를 지정한다(최신 문자열의 UTF-16 인덱스, end 제외). 도구가 범위 앞뒤 문자열의 보존을 강제한다. 필드 전체 수정이면 range를 생략한다. 범위를 사용자 요청과 맞게 정했는지는 사람이 diff와 함께 검토한다.

`scope.json`은 요청과 명시적으로 허용된 leaf를 기록한다. `path`는 **block.data 기준** RFC 6901 pointer다. 정확한 page/block ID와 기존 필드만 허용한다.

```json
{
  "request": "소개 문구만 수정",
  "targets": [{ "pageId": "p_current", "blockId": "b_intro", "path": "/text" }]
}
```

`plan.json`은 `hash latest.json` 결과와 정확한 이전 값, 후보, 이유, 출처 참조를 갖는다. `evidence`는 실제 facts ID나 사용자 표현 수정 요청 참조다. 이 참조는 도구에서 존재나 진실성을 검증하지 않으므로 별도 대조한다.

```json
{
  "baseHash": "<hash 명령의 SHA-256>",
  "operations": [{
    "pageId": "p_current", "blockId": "b_intro", "path": "/text",
    "expected": "기존 소개", "value": "검토한 새 소개",
    "reason": "사용자가 요청한 표현 수정", "evidence": ["user-request:소개 표현 수정"]
  }]
}
```

원본의 **파일 바이트** SHA-256이 기준이므로 공백만 재저장해도 hash를 다시 얻어야 한다. hash를 갱신했다고 오래된 expected를 버리지 않는다. 충돌은 실행 중단 사유이며 새 export와 사용자의 요청을 다시 대조한다.

`propose`는 아직 없는 디렉터리만 생성한다. `original.json`(바이트 그대로), `candidate.json`, `changes.json`(이전/이후·이유·근거·hash), `scope.json`, `plan.json`이 생성된다. 잘못된 스키마/타입/중복 ID/미지원 블록/필드·테마를 거절하며 변환하거나 버리지 않는다. `verify`는 후보 전체를 재구성해 비교하므로 요청 밖 텍스트·블록·순서·테마 변경도 거절한다.

## 앱 왕복과 제출 점검

1. 최초 작성은 AI가 생성한 `resume-v1.json`을, 후속 수정은 원본 전체 JSON과 diff를 대조한 `candidate.json`을 앱의 공유 → JSON 붙여넣기 → 가져오기로 **새 이력서**로 가져온다.
2. 시각 편집 후 JSON 복사를 통해 새 파일로 저장한다. 페이지/블록 ID 재발급을 확인하고 다음 수정은 이 export 기준으로 한다. 이전 scope/plan은 재사용하지 않는다.
3. 새 export에 validator를 실행한다. 비공개 사실/근거와 문장을 대조하고 빈 항목·예시 문구·요청 밖 변경을 확인한다.
4. 앱 overflow 경고와 화면의 각 페이지 하단을 확인한다. 고정 A4의 print CSS는 초과 내용을 숨길 수 있다. 분량은 앱에서 줄이거나 페이지를 나눈다.
5. 앱 PDF 버튼의 `window.print()`로 저장한다. PDF의 페이지 수·가장자리·한글·링크 목적지를 시각 확인하고, 텍스트 추출의 한글/문장 누락/읽기 순서를 대조한다. 브라우저 자동 인쇄만 확인했다면 OS 인쇄 대화상자 수동 검증과 구분한다.
6. 실제 확인한 범위/미확인 항목과 사실 질문을 보고한다. 스키마 통과만으로 제출 가능 판정을 내리지 않는다.
